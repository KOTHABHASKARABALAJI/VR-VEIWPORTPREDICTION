1.1 Problem Statement & Real-World Motivation:
In standard video streaming, a flat 2D video is displayed on a screen, and the entire video frame is
visible to the user. In contrast, 360-degree virtual reality (VR) video is captured as an omnidirectional
spherical panorama (often stored in Equirectangular Projection format, ERP) at ultra-high resolutions
such as 4K (3840x1920 / 3840x2160) or 8K. 

Streaming an entire 360-degree 4K/8K sphere requires immense network bandwidth (often 50 to 100+ Mbps),
which strains mobile cellular networks and home broadband. However, when a user wears a Head-Mounted
Display (HMD) like an HTC Vive or Oculus Quest, human visual biology restricts their Field of View (FoV)
to only about 90 to 110 degrees diagonally at any single instant. This visible area is called the VIEWPORT.

The user only ever looks at approximately 15% to 20% of the full 360-degree spherical canvas at any
given millisecond. Transmitting the remaining 80% to 85% of the panorama in full ultra-high quality is
massively wasteful. 

To solve this problem, modern 360-degree streaming uses TILE-BASED STREAMING:
1. The 360-degree video frame is chopped spatially into an M x N grid of rectangular tiles.
2. A machine learning model predicts where the user will rotate their head a short time in advance
   (e.g., 0.5 seconds ahead).
3. The streaming system requests and downloads tiles inside the predicted viewport at maximum resolution
   (high bitrate), while transmitting peripheral/background tiles at low resolution or omitting them.
4. If the prediction is accurate, the user experiences crisp, crystal-clear VR immersion with zero buffering,
   while total bandwidth consumption is slashed by 40% to 70%.

The goal of this project codebase is to develop, train, validate, and compare deep recurrent neural networks
(LSTM and GRU) to predict future head rotation viewports (yaw and pitch orientation) from user motion history.


1.2 End-to-End System Workflow Architecture:
The actual implemented workflow inside this repository follows 8 discrete, sequential stages:

Stage 1: Dataset Acquisition & Download
- Script: download_src_info.py
- Action: Automates the HTTP download of 20 video source metadata JSON files (1.json to 20.json) from
  the public GitHub repository of the AVTrack360 dataset into the local directory 'SRC_info/'.

Stage 2: Video Metadata Extraction
- Script: extract_video_metadata.py
- Action: Parses FFprobe stream and format metadata from the 20 downloaded JSON files, extracting
  width, height, resolution, frame rate, duration, container format, and bitrates into 'video_metadata.csv'.

Stage 3: Raw Viewport Trajectory Harvesting & Ingestion
- Directory: Head_rotation/ (48 JSON files: 2.json to 49.json)
- Script: combine_viewport_data.py
- Action: Reads head tracking logs recorded from 48 human subjects wearing HTC Vive HMDs watching 20 videos.
  Extracts 284,247 timestamped head rotation records (sec, pitch, yaw, roll) into 'combined_viewport_data.csv'.

Stage 4: Data Validation & Exploratory Movement Dynamics Analysis
- Scripts: analyze_unique_videos.py, verify_csv.py
- Artifacts: viewport_data_analysis.txt, viewport_movement_analysis.txt, trajectory_summary.csv,
  viewport_movement_analysis.csv, unique_videos.csv, viewport_trajectories.csv
- Action: Identifies 960 discrete trajectories (48 subjects x 20 videos). Discovers that sampling interval is
  quasi-uniform at ~10 Hz (mean dt = 100.91 ms). Computes angular velocities and accelerations, 360-degree
  yaw wrap-around frequencies, displacement statistics across time lags (0.1s to 3.0s), and autocorrelation.
  Concludes that a 1.0-second input history (10 frames) and a 0.5-second prediction horizon (5 frames)
  provide optimal predictive inertia.

Stage 5: Feature Engineering, Sequence Generation & Disjoint Subject Splitting
- Artifacts: lstm_train.npz, lstm_validation.npz, lstm_test.npz, lstm_subject_split.csv, lstm_dataset_summary.txt
- Action: Generates sliding window input sequences of shape (10, 7) and prediction targets (3,).
  Engineers 7 features: [sin_yaw, cos_yaw, pitch, yaw_vel, pitch_vel, yaw_acc, pitch_acc].
  Transforms yaw angles into continuous trigonometric coordinates [sin(yaw), cos(yaw)] to eliminate boundary
  discontinuity. Performs a strictly subject-independent split: 33 subjects (186,176 samples) for training,
  7 subjects (39,506 samples) for validation, and 8 subjects (45,125 samples) for testing. Computes Z-score
  normalization strictly on the training set to prevent data leakage.

Stage 6: Multi-Model Architecture Construction & Training
- Script: compare_models.py
- Framework: PyTorch (torch, torch.nn)
- Action: Builds and trains 4 deep recurrent neural network architectures:
  - Model A: LSTM-64 baseline (1 LSTM layer with 64 units, 1 Dense layer with 32 units, ReLU, Linear output)
  - Model B: LSTM-128 (1 LSTM layer with 128 units, 1 Dense layer with 32 units, ReLU, Linear output)
  - Model C: GRU-64 (1 GRU layer with 64 units, 1 Dense layer with 32 units, ReLU, Linear output)
  - Model D: LSTM with Dropout (1 LSTM layer with 64 units, Dropout p=0.2, 1 Dense layer with 32 units, ReLU, Linear output)
  All models are trained with Adam optimizer (lr=0.001), Mean Squared Error (MSE) loss, batch size 256,
  up to 100 epochs, with early stopping (patience=10 epochs monitoring validation loss) and restoring best weights.

Stage 7: Model Comparison & Selection
- Script: compare_models.py
- Artifacts: model_comparison.csv, model_comparison_report.txt, model_comparison_training_curves.png,
  best_viewport_model.pth
- Action: Compares all 4 models on the validation set using Circular Yaw MAE/RMSE, Pitch MAE/RMSE, and
  Great-Circle Spherical Angular Error (MAE, median, 90th percentile). Model C (GRU-64) achieves the lowest
  validation Spherical MAE (9.7289°) and is selected as the winning architecture. Its weights are saved.

Stage 8: Final Independent Test Set Evaluation
- Script: compare_models.py
- Artifacts: best_model_test_metrics.txt, best_model_test_predictions.csv
- Action: Evaluates the winning GRU-64 model on the completely unseen 8 test subjects (45,125 samples).
  Measures Yaw MAE = 8.2482°, Pitch MAE = 3.6847°, Spherical MAE = 9.5525°, Spherical Median = 6.8841°.
  Exports frame-by-frame actual vs. predicted coordinates and error distributions.

4.1 Dataset Origin and Organization (AVTrack360):
- Origin: The dataset is drawn from the publicly available AVTrack360 (Audio-Visual Tracking in 360° Video)
  benchmark dataset published at ACM MMSys 2018.
- Subjects: Exactly 48 distinct human participants (identified as subjects 2 through 49).
- Videos: Exactly 20 distinct omnidirectional videos (1.mp4 through 20.mp4), each approximately 30 seconds long.
- Trajectories: 48 subjects x 20 videos = Exactly 960 unique viewing trajectories.
- Total Samples: 284,247 raw timestamped orientation data points. Each trajectory contains approximately
  295 to 297 consecutive samples recorded at ~10 Hz (mean interval = 100.91 ms).


4.2 Data Cleaning, Missing Values, and Invalid Data:
- Missing Values: Zero missing values exist across all columns (video, hmd, timestamp, pitch, yaw, roll).
  Every record contains complete numerical data.
- Range Integrity:
  - Yaw: Strictly in [-180°, +180°] (valid spherical azimuth).
  - Pitch: Strictly in [-87°, +86°] (valid spherical elevation, within the theoretical [-90°, +90°] limits).
  - Timestamps: Non-negative, spanning 0.000s to 30.096s.
- Duplicate Rows: 39 exact duplicate rows were detected in combined_viewport_data.csv. They represent minor
  sensor recording redundancies and do not disrupt sequential continuity.


4.3 Handling Pitch, Yaw, and Roll:
- Roll: In VR headsets, roll represents lateral tilting of the head towards the shoulders. In normal 360° video
  viewing, users rarely tilt their heads laterally (mean roll in the dataset is 0.51° with 99% of values
  between -14° and +15°). Because the center of the viewport is governed entirely by azimuth (yaw) and
  elevation (pitch), roll does not change the center orientation of the viewport. Therefore, roll is omitted
  from the predictive model features to reduce dimensionality.
- Pitch: Represents looking up (positive pitch up to +90°) and looking down (negative pitch down to -90°).
  Pitch is a bounded linear angle that does not wrap around.
- Yaw: Represents looking left and right across 360 degrees. Yaw wraps around at -180° and +180°.


4.4 The 7 Engineered Input Features:
For every timestep t, a feature vector of length 7 is constructed:
Feature 1: sin_yaw   = sin(radians(yaw_t))
Feature 2: cos_yaw   = cos(radians(yaw_t))
Feature 3: pitch     = pitch_t (in degrees)
Feature 4: yaw_vel   = (unwrapped_yaw_t - unwrapped_yaw_{t-1}) / delta_t  (in deg/s)
Feature 5: pitch_vel = (pitch_t - pitch_{t-1}) / delta_t  (in deg/s)
Feature 6: yaw_acc   = (yaw_vel_t - yaw_vel_{t-1}) / delta_t  (in deg/s²)
Feature 7: pitch_acc = (pitch_vel_t - pitch_vel_{t-1}) / delta_t  (in deg/s²)


4.5 Why Yaw Uses Sine and Cosine (Trigonometric Encoding):
In spherical geometry, yaw angle is circular: -180° and +180° describe the EXACT SAME physical orientation
(looking directly backwards).
If raw degree values are fed directly to a neural network:
- A user rotating their head slightly from +179° to -179° makes a tiny physical turn of only 2 degrees.
- However, as raw numbers, the angle jumps from +179 to -179 — an apparent numeric change of 358!
- The neural network's loss function (Mean Squared Error) would penalize this jump as an enormous error:
  (179 - (-179))^2 = 358^2 = 128,164!
- This causes violent gradient spikes, destabilizes backpropagation, and destroys model convergence.

By encoding yaw as a 2D unit vector on the unit circle:
- sin(179°) = 0.0175,   cos(179°) = -0.9998
- sin(-179°) = -0.0175,  cos(-179°) = -0.9998
The Euclidean distance between these two vectors is tiny (approx 0.035), matching the true physical rotation.
At prediction time, the model predicts [pred_sin, pred_cos], and the continuous yaw angle is reconstructed
unambiguously using the four-quadrant inverse tangent:
  pred_yaw_deg = degrees(arctan2(pred_sin, pred_cos))


4.6 Calculation of Velocity and Acceleration:
When calculating angular velocity, if yaw wraps from +179° to -179° in 0.1s, a naive difference yields:
  (-179 - 179) / 0.1 = -3580 deg/s (a massive false velocity spike!).
To solve this, the codebase unwraps the yaw trajectory before computing derivatives:
  unwrapped_yaw = unwrap(radians(yaw)) * (180 / pi)
The unwrapping algorithm detects jumps greater than pi (180°) and adds or subtracts multiples of 360° to make
the trajectory continuous. Then:
  yaw_vel = d(unwrapped_yaw) / dt
  yaw_acc = d(yaw_vel) / dt


4.7 Sequence Generation: 10-Frame History and 5-Frame Horizon:
- Input Sequence Length (L = 10 frames):
  At the dataset's sampling frequency of ~10 Hz (dt = 0.1s), 10 frames represent exactly 1.0 second of history.
  The autocorrelation analysis proved that head position autocorrelation remains extremely high (r = 0.86 to 0.99)
  and velocity autocorrelation remains positive (r = 0.26) across 1.0 second. This gives the recurrent network
  sufficient context to capture movement inertia, acceleration trends, and directional intent without introducing lag.
- Prediction Horizon (k = 5 frames ahead):
  5 frames ahead at 10 Hz represents 0.5 seconds into the future. In video streaming, 0.5s corresponds to the
  typical network segment buffer and download round-trip time (RTT). Predicting 0.5s ahead allows the video player
  to request the appropriate spatial tiles before the user actually turns their head.
- Sequence Matrix Generation:
  For each trajectory of length T:
  - Input X[i]: frames i to i+9 (shape 10 x 7).
  - Target y[i]: frame i+14 (0.5s into the future, 5 steps after the last observed frame i+9).
  - Boundary Protection: No sequence crosses subject or video boundaries. The last 14 frames of each trajectory
    (9 history + 5 horizon) cannot form a complete sequence, yielding 14 discarded boundary samples per trajectory
    (14 x 960 = 13,440 discarded samples total).
  - Total Valid Generated Samples across dataset: 270,807 samples.


4.8 Normalization Method (Z-Score Standard Normalization):
Neural networks train fastest and most reliably when input features have zero mean and unit variance.
The codebase applies Z-Score Standardization:
  X_normalized = (X - norm_mean) / norm_std
CRITICAL RULE TO PREVENT DATA LEAKAGE:
The normalization parameters (mean and std) were calculated STRICTLY on the training split (33 subjects) only.
The validation and test sets were scaled using the training set's mean and std:
  - sin_yaw   : mean = -0.0287, std = 0.6410
  - cos_yaw   : mean =  0.2772, std = 0.7144
  - pitch     : mean = -0.0581, std = 18.8304
  - yaw_vel   : mean =  0.3947, std = 42.1019
  - pitch_vel : mean =  0.0188, std = 18.9996
  - yaw_acc   : mean =  0.0533, std = 165.6945
  - pitch_acc : mean = -0.0083, std = 111.0671
These parameters are stored inside the NPZ files and used at test time to normalize target pitch and
un-normalize predictions.


4.9 Subject-Independent Data Splitting (Preventing Data Leakage):
In machine learning, if data points from the same user are placed in both the training set and the test set,
the model can memorize the user's personal viewing habits (e.g., how fast they tilt their head), leading to
artificially high accuracy that collapses when tested on a new user in the real world.
To prevent this, the codebase uses a SUBJECT-INDEPENDENT (disjoint) split:
- 48 total subjects are partitioned into 3 non-overlapping sets:
  - Training Set (33 subjects, ~70%): Subjects [2, 3, 5, 6, 7, 8, 10, 11, 13, 14, 15, 17, 18, 19, 21, 23,
    26, 27, 28, 29, 31, 32, 33, 34, 35, 36, 39, 41, 42, 45, 46, 47, 48] -> 186,176 samples.
  - Validation Set (7 subjects, ~15%): Subjects [4, 12, 24, 25, 37, 38, 43] -> 39,506 samples.
  - Test Set (8 subjects, ~15%): Subjects [9, 16, 20, 22, 30, 40, 44, 49] -> 45,125 samples.
Zero subjects overlap between splits.


4.10 Feature Engineering vs. Formal Feature Selection:
- Feature Engineering: DEFINITELY PERFORMED. Raw head data contained only [pitch, yaw, roll, sec].
  The codebase engineered 7 sophisticated kinematic features: trigonometric coordinates [sin_yaw, cos_yaw],
  first-order angular velocities [yaw_vel, pitch_vel], and second-order angular accelerations [yaw_acc, pitch_acc].
- Formal Feature Selection: NOT PERFORMED. No algorithmic feature selection (such as SelectKBest, Recursive
  Feature Elimination / RFE, LASSO L1 regularization, VarianceThreshold, or PCA) was executed. All 7 engineered
  features were retained and passed into the recurrent networks.

- Layer 3: nn.Linear(in_features=32, out_features=3)

- Layer 3: nn.Linear(in_features=32, out_features=3)

- Layer 3: nn.Linear(in_features=32, out_features=3)

5.3 Common Training Configuration:
- Optimizer: Adam (Adaptive Moment Estimation)
  - Learning Rate: 0.001
  - Adam computes adaptive learning rates for each parameter using first and second gradient moments.
- Loss Function: Mean Squared Error (MSE Loss)
  - L = (1 / 3N) * sum_i [ (pred_sin - true_sin)^2 + (pred_cos - true_cos)^2 + (pred_norm_pitch - true_norm_pitch)^2 ]
  - Directly minimizes Euclidean distance between predicted and target output vectors.
- Batch Size: 256 samples per mini-batch.
- Maximum Epochs: 100 epochs.
- Early Stopping:
  - Patience = 10 epochs.
  - Monitors validation loss at the end of every epoch.
  - If validation loss does not reach a new minimum for 10 consecutive epochs, training terminates early.
  - Best Weights Restoration: Clones model.state_dict() at the best epoch and restores these optimal weights
    at the end of training.
- Random Seed: SEED = 42 (fixed across Python random, NumPy, and PyTorch for exact reproducibility).

SECTION 6: EVALUATION METRICS AND MODEL COMPARISON
====================================================================================================

6.1 Mathematical Formulation of Evaluation Metrics:

1. Circular Yaw Mean Absolute Error (Yaw MAE):
   Because yaw wraps around at +/-180°, direct absolute difference |pred - act| produces false errors at the boundary.
   The circular difference is computed as:
     yaw_diff = | (pred_yaw - act_yaw + 180) mod 360 - 180 |
     Yaw MAE = (1 / N) * sum(yaw_diff)
   Units: Degrees (°).

2. Circular Yaw Root Mean Squared Error (Yaw RMSE):
     Yaw RMSE = sqrt( (1 / N) * sum(yaw_diff^2) )
   Penalizes large outlier yaw prediction errors more heavily than MAE.

3. Pitch Mean Absolute Error (Pitch MAE):
     pitch_diff = | pred_pitch - act_pitch |
     Pitch MAE = (1 / N) * sum(pitch_diff)
   Units: Degrees (°).

4. Pitch Root Mean Squared Error (Pitch RMSE):
     Pitch RMSE = sqrt( (1 / N) * sum(pitch_diff^2) )


6.2 Great-Circle Spherical Angular Error (Orthodromic Distance):
In a 360° VR headset, evaluating yaw and pitch independently is insufficient because a 5° yaw error at the
equator represents a much larger physical visual displacement than a 5° yaw error near the poles.
The true physical error between two viewports on the 3D unit sphere is the GREAT-CIRCLE DISTANCE:
- Let the actual viewport center have pitch p1 and yaw y1 (converted to radians).
- Let the predicted viewport center have pitch p2 and yaw y2 (converted to radians).
- In 3D Cartesian coordinates, the unit vectors are:
    u1 = [cos(p1)*cos(y1),  cos(p1)*sin(y1),  sin(p1)]
    u2 = [cos(p2)*cos(y2),  cos(p2)*sin(y2),  sin(p2)]
- Their inner dot product is:
    dot = u1 · u2 = sin(p1)*sin(p2) + cos(p1)*cos(p2)*cos(y1 - y2)
- Clipping: dot = clip(dot, -1.0, 1.0) to prevent numerical rounding beyond [-1, 1].
- Great-Circle Angular Error (degrees):
    sph_err_deg = degrees( arccos(dot) )
- Metrics computed on spherical error:
  - Spherical MAE (Mean Error)
  - Spherical Median Error (50th percentile)
  - Spherical 90th Percentile Error (error threshold containing 90% of all predictions)
  - Spherical RMSE

6.6 Practical Limitations of the Current Evaluation:
1. Motion-Only Modality: The models rely purely on historical head orientation kinematics. They do not incorporate

   longer horizons (> 1.5 seconds).
2. Horizon Boundary: Predictions are evaluated at a fixed 0.5-second horizon. Adaptive multi-horizon prediction
   (e.g., dynamically predicting 0.2s, 0.5s, 1.0s, and 2.0s simultaneously) is not implemented.
3. Regression Task: Accuracy percentages (e.g., "95% accuracy") are mathematically inapplicable to continuous
   angular regression tasks; performance must strictly be expressed in angular error (degrees).

Q1: What is the primary objective of this project?
Ans: The objective is to predict future viewport orientations (head rotations in yaw and pitch) of users
watching 360-degree VR videos 0.5 seconds in advance using recurrent deep learning models, enabling tile-based
adaptive streaming that saves network bandwidth without degrading user visual quality.

Q2: Why is tile-based streaming necessary for 360-degree video?
Ans: 360-degree video frames are massive (4K or 8K panoramas) requiring 50 to 100+ Mbps bandwidth. However,
a VR headset user only views a 90° to 110° Field of View (approximately 15% to 20% of the sphere) at any instant.
Tile-based streaming divides the frame into spatial tiles, downloading only the user's visible tiles in high
resolution and peripheral tiles in low resolution, cutting bandwidth usage by 40% to 70%.

Q3: Which deep learning framework is actually used in the code?
Ans: PyTorch (torch, torch.nn, torch.utils.data) is used for all model construction, training, gradient descent,
and evaluation. Model checkpoint files in saved_models/ ('best_viewport_model.pth' and 'viewport_lstm_model.pth')
are PyTorch serialized state dictionaries loaded with torch.load().

Q4: What libraries are directly imported across your Python scripts?
Ans: Standard library modules: pathlib, json, urllib.request, time, os, random.
Third-party libraries: pandas, numpy, torch (including torch.nn and torch.utils.data), and matplotlib.pyplot.
TensorFlow, Scikit-learn, and OpenCV are NOT directly imported.

Q5: What dataset did you use, and what is its structure?
Ans: We used the public AVTrack360 benchmark dataset (ACM MMSys 2018). It contains head tracking logs from 48
human subjects (subjects 2 to 49) watching 20 omnidirectional videos (~30s each) on HTC Vive HMDs, yielding
960 discrete viewing trajectories and 284,247 timestamped records sampled at ~10 Hz (every ~100 ms).

Q6: What are the input features fed into the model?
Ans: Exactly 7 engineered kinematic features:
1. sin_yaw: sin(radians(yaw))
2. cos_yaw: cos(radians(yaw))
3. pitch: elevation angle in degrees
4. yaw_vel: angular velocity of yaw in deg/s (computed on unwrapped yaw)
5. pitch_vel: angular velocity of pitch in deg/s
6. yaw_acc: angular acceleration of yaw in deg/s²
7. pitch_acc: angular acceleration of pitch in deg/s²

Q7: What is the shape of the model's input tensor?
Ans: The input shape is (Batch_Size, 10, 7), representing 10 historical timesteps (1.0 second at 10 Hz) with
7 features per timestep.

Q8: What does the model output, and what is the target tensor shape?
Ans: The target shape is (Batch_Size, 3). The model outputs 3 continuous numbers:
[sin(future_yaw), cos(future_yaw), normalized_future_pitch], predicting the head orientation 5 frames (0.5s) ahead.

Q9: Why did you omit the 'roll' angle from model inputs?
Ans: In VR head tracking, roll represents tilting the head sideways toward the shoulders. In 360° video viewing,
roll is negligible (mean 0.51°, 99% within [-14°, +15°]) and does not alter the center coordinates of the
directional viewport on the sphere. Omitting roll reduces input dimensionality without losing predictive power.

Q10: Why did you represent yaw as sine and cosine instead of raw degree values?
Ans: Because yaw is a circular angle with boundary wrap-around at +/-180°. A user turning 2 degrees from +179°
to -179° creates an artificial jump of 358° in raw numbers, causing massive MSE loss spikes (358^2 = 128,164)
and destabilizing gradient descent. Encoding yaw as [sin(yaw), cos(yaw)] provides a continuous 2D coordinate on
the unit circle with zero boundary discontinuity.

Q11: How do you reconstruct the yaw angle in degrees from model predictions?
Ans: Using the four-quadrant inverse tangent:
pred_yaw_deg = np.degrees(np.arctan2(pred_sin, pred_cos)), which correctly restores angles in (-180°, +180°].

Q12: Why did you unwrap yaw when calculating velocity and acceleration?
Ans: When a user crosses the +/-180° boundary, a raw difference between consecutive frames (-179° - 179°)
produces a false velocity spike of -3580 deg/s. Unwrapping converts circular angles into a continuous monotonic
curve, allowing true physical derivatives to be computed.

Q13: Why did you choose a 10-frame history window and a 5-frame prediction horizon?
Ans: Autocorrelation analysis in viewport_movement_analysis.txt showed that head position autocorrelation is
very high (r > 0.86 to 0.99) and velocity autocorrelation is positive (r = 0.26) within 1.0s (10 frames at 10 Hz).
10 frames captures velocity trends and acceleration inertia without lag. 5 frames (0.5s ahead) matches the typical
video streaming buffer and chunk fetch latency.

Q14: How did you partition the dataset into training, validation, and test sets?
Ans: We performed a subject-independent split across the 48 participants:
- Training: 33 subjects (~70%, 186,176 samples)
- Validation: 7 subjects (~15%, 39,506 samples)
- Test: 8 subjects (~15%, 45,125 samples)

Q15: What is data leakage, and how did you prevent it?
Ans: Data leakage occurs when information from the test set inadvertently influences model training, yielding
optimistic but false test scores. We prevented leakage in two ways:
1. Subject-disjoint splitting: Test subjects were never seen during training, ensuring the model generalizes
   to new users rather than memorizing individual viewing habits.
2. Normalization: Z-score mean and std parameters were computed strictly on the training split, never on validation/test.

Q16: Did you perform formal feature selection?
Ans: No. We performed feature engineering (deriving sine/cosine coordinates, velocities, and accelerations),
but all 7 engineered features were retained. No statistical or algorithmic feature elimination (like RFE,
SelectKBest, or PCA) was performed.

Q17: Why did you use Long Short-Term Memory (LSTM) and GRU networks?
Ans: Human head motion is sequential time-series data with temporal inertia. Feed-forward networks treat frames
independently and ignore temporal order. Standard RNNs suffer from vanishing gradients. LSTM and GRU contain
memory cells and gating mechanisms that retain historical motion patterns across sequential timesteps.

Q18: What is the difference between LSTM and GRU in your implementation?
Ans: LSTM uses 3 gates (Forget, Input, Output) and maintains separate cell and hidden states (20,835 parameters
in Model A). GRU merges cell and hidden states and uses only 2 gates (Reset and Update), requiring 16,035 parameters
in Model C — a 23% reduction in parameters, resulting in faster inference.

Q19: What architectures were compared in compare_models.py?
Ans: Four architectures:
1. Model A: LSTM-64 (LSTM(64) -> Linear(64->32, ReLU) -> Linear(32->3))
2. Model B: LSTM-128 (LSTM(128) -> Linear(128->32, ReLU) -> Linear(32->3))
3. Model C: GRU-64 (GRU(64) -> Linear(64->32, ReLU) -> Linear(32->3))
4. Model D: LSTM with Dropout (LSTM(64) -> Dropout(0.2) -> Linear(64->32, ReLU) -> Linear(32->3))

Q20: Why did you use Adam optimizer and MSE loss?
Ans: Adam adaptively adjusts individual learning rates for each weight parameter using momentum, providing
rapid and stable convergence. MSE (Mean Squared Error) directly penalizes Euclidean distance between predicted
and target output coordinates on continuous regression targets.

Q21: What was your training configuration (learning rate, batch size, epochs, early stopping)?
Ans: Learning rate = 0.001, Batch size = 256, Maximum epochs = 100, Early stopping patience = 10 epochs
monitoring validation loss, with best weight restoration enabled.

Q22: Which model performed best, and why was it selected?
Ans: Model C (GRU-64) was selected because it achieved the lowest Validation Spherical Mean Absolute Error
(9.7289°) and lowest validation MSE loss (0.053500) at Epoch 6. It also uses 23% fewer parameters than LSTM-64.

Q23: What results did the selected GRU-64 model achieve on the independent test set?
Ans: On 45,125 test samples from 8 unseen subjects:
- Yaw MAE: 8.2482 degrees
- Pitch MAE: 3.6847 degrees
- Spherical MAE (Great-Circle): 9.5525 degrees
- Spherical Median Error: 6.8841 degrees
- Spherical 90th Percentile Error: 20.0725 degrees

Q24: What is Great-Circle Spherical Angular Error, and why is it used instead of Euclidean error?
Ans: In 3D VR, a head rotation is an orientation on a unit sphere. A 5° yaw error at the equator covers a much
larger physical visual distance than a 5° yaw error near the pole. Great-Circle error measures the true orthodromic
angular distance between the predicted unit vector u1 and actual unit vector u2:
  error = arccos(u1 · u2) = arccos( sin(p1)*sin(p2) + cos(p1)*cos(p2)*cos(y1 - y2) ).

Q25: Can you report an "accuracy percentage" (e.g., 95%) for this model?
Ans: No. This is a continuous numerical regression problem predicting 3D angles, not a categorical classification
problem. In regression, reporting an arbitrary percentage is technically invalid unless a tolerance threshold
is explicitly defined. Model quality is measured in Mean Absolute Error (degrees).

Q26: How did Model B (LSTM-128) perform compared to Model A (LSTM-64)?
Ans: Model B performed slightly worse (validation Spherical MAE of 9.8698° vs 9.7504° for Model A). Doubling
hidden units to 128 increased parameters to 73,923 without improving accuracy, exhibiting slight overfitting.

Q27: How did Model D (Dropout) perform?
Ans: Model D converged slower (best epoch at 21 vs 9 for Model A) and achieved a validation Spherical MAE of 9.7736°.
Dropout did not improve performance because the subject-disjoint dataset was already sufficiently large and
generalized well without heavy regularization.

Q28: Why is pitch MAE (3.68°) significantly lower than yaw MAE (8.25°)?
Ans: Biomechanically, human head movement is heavily biased toward horizontal exploration (looking left and right)
rather than vertical neck tilting. The dataset dynamics showed mean pitch velocity is only 10.3°/s compared to
26.8°/s for yaw, making pitch more static and easier to predict.

Q29: Which parts of the project title are completed, and which parts remain unfinished?
Ans: Completed: Viewport trajectory analysis, feature engineering, sequence formulation, subject-disjoint splitting,
and ML-based viewport prediction modeling (LSTM and GRU) with comprehensive spherical evaluation.
Unfinished: Spatial tiling of the 360° video (dividing frames into tile grids), viewport-to-tile intersection
mapping, and adaptive quality/bitrate allocation algorithms.

Q30: What are the main limitations of your current implementation?
Ans:
1. Motion-only modality: It does not use visual video saliency (objects, faces, movement) to guide predictions.
2. Fixed horizon: It predicts at a single fixed horizon of 0.5s rather than multi-step horizons.
3. Tiling and network simulation are not yet integrated end-to-end.
